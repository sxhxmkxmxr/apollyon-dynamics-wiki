Flight Software Stack

The flight-critical loop runs on a proprietary autopilot that is set up through configuration — Embention's Veronte Autopilot 1x. Apollyon writes the control laws, guidance, envelope protection and mission logic that sit on top, and tests each build on hardware-in-the-loop before it flies.

01 · Foundation

A proprietary flight-control baseline

Defence certification in India rules out a community open-source autopilot. The flight-critical core needs a named owner, a clear record of where it came from, and a vendor responsible for it through its life.

Apollyon therefore builds on Embention's Veronte Autopilot 1x, a proprietary flight controller that is set up through configuration rather than code changes. It is already used across uncrewed aircraft. We chose a commercial baseline over an open-source stack for three reasons: the software has a named owner and a documented history, its changes are controlled, and the vendor supports it across its lifecycle.

The baseline is not modified at source

Apollyon does not change the autopilot firmware itself. The engineering work lives in a versioned configuration package—control laws, guidance phases, envelope limits, allocation matrices and safety logic—written in the vendor's engineering environment and uploaded to the flight controller. One baseline, one package per airframe.

02 · Toolchain

Authored, executed, operated, verified

The toolchain has four stages and one configuration. The package we write on the bench is the package that flies and the package that is verified. Nothing is rewritten between engineering and the airframe.

The four stages

Author1x PDI BuilderControl laws, guidance phases, envelope limits, actuation allocation and safety logic assembled as block programs.
ExecuteVeronte Autopilot 1xFlight-critical guidance, navigation and control, state estimation and actuator commands.
OperateVeronte OpsMission planning, telemetry, commanded actions, flight termination and alerts.

03 · The authored layer

What Apollyon authors

The baseline provides the framework. The capability comes from what Apollyon configures on it: the control and mission logic that adapts a general-purpose controller to each vehicle.

Ownership across the stack
LayerOwnerContent
Mission & autonomyApollyonRoute and terrain following, terminal-phase sequencing, target re-acquisition, abort and failsafe triggers.
Control & guidance lawsApollyonGain schedules, envelope limits, control-loop tuning and actuation allocation matrices per airframe.
Safety configurationApollyonFlight-termination logic, safety-bit conditions, phase checklists and configuration locks.
Guidance–navigation–control coreEmbention VeronteState estimation, guidance modes, control execution, mixing and real-time scheduling.
Drivers, I/O & hardwareEmbention VeronteSensor drivers, bus and protocol support, the autopilot hardware itself.
Why the configuration layer matters

An airframe is defined by its configuration package, so it does not need a separate build. Any improvement to the baseline can be applied to every platform that shares it. Building a new vehicle then costs only the difference in its package, which is measured against the shared physics backbone.

04 · Verification

Hardware-in-the-loop before the rail

No configuration flies until it has passed on the bench. The Veronte HIL Simulator runs the production autopilot against a simulated vehicle, so the flight controller under test is the same unit that will fly.

The autopilot receives simulated navigation and sensor data and returns real actuator commands. Control laws, guidance logic and failsafes therefore run exactly as they will in flight.

Simulation back-ends
Back-endWhat it tests
X-Plane 11 / 12Flight dynamics and control performance for fixed-wing, multirotor and VTOL models.
Microsoft Flight SimulatorExtra flight-dynamics coverage and operator training.
SimulinkCustom plant models and engineering tests connected directly to the autopilot.

Faults and degraded conditions—jammed surfaces, sensor dropouts, loss of navigation, electronic-warfare interference—are injected on the bench against the same software that will fly. Each sortie then returns high-rate telemetry that feeds the physics backbone and the next tuning cycle. The sim-to-real flight loop →

05 · Governance

Configuration control and certification

A proprietary baseline supports certification as well as engineering. It gives the flight-critical core a vendor-maintained history and a configuration process that can be audited.

Every Apollyon configuration package is versioned, reviewed and released under change control. The autopilot supports locked configurations and per-phase checklists, so a released package cannot be changed in the field without the matching control action. This leaves a clear record from the authored block program to the uploaded configuration and the flight log.

Certification basis

The flight-control baseline is supplied with vendor compliance and lifecycle documentation, which Apollyon keeps as part of the platform's certification evidence. Qualification and airworthiness claims are made only against that documentation, not derived from the engineering tools.
